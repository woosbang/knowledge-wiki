01

개발 브랜치 생성

운영 코드가 있는 main 브랜치를 직접 수정하지 않습니다. 별도의 feature 브랜치를 만들어 독립된 공간에서 작업합니다.

Terminal 
# 최신 상태 동기화
git checkout main
git pull origin main

# 작업용 브랜치 생성 및 이동
git checkout -b feature/새기능이름
💡
브랜치 이름은 feature/add-search, fix/login-bug처럼 작업 내용을 알 수 있게 짓는 것이 좋습니다.
02

Supabase 개발용 프로젝트 생성

운영 Supabase 프로젝트에서 직접 개발하면 안 됩니다. 개발 전용 프로젝트를 별도로 만들어 사용합니다. 모든 작업은 Supabase 대시보드에서 진행합니다.

⚠️
운영 DB에서 직접 개발하면 실수로 사용자 데이터가 삭제되거나 테이블 구조가 깨질 수 있습니다. Auth 설정이 꼬이면 기존 사용자가 로그인 불가 상태에 빠질 수도 있습니다.

A. 새 프로젝트 생성

  1. supabase.com/dashboard 접속 → New Project 클릭
  2. 프로젝트 이름을 myapp-dev 등 구분 가능하게 지정
  3. 리전(Region)은 운영 프로젝트와 동일하게 선택 (성능 차이 방지)
  4. DB 비밀번호 설정 후 프로젝트 생성 완료

B. 운영 테이블 구조(스키마) 복제

운영 프로젝트에서 테이블 구조만 복사하여 개발 프로젝트에 적용합니다. 실제 사용자 데이터는 가져오지 않습니다.

  1. 운영 프로젝트 대시보드 → SQL Editor 에서 아래 쿼리를 실행하여 각 테이블의 전체 DDL(CREATE TABLE 문)을 확인합니다
  2. 출력된 DDL을 모두 복사합니다
  3. 개발 프로젝트 대시보드 → SQL Editor 에 붙여넣기 후 실행합니다
SQL — 운영 프로젝트 SQL Editor에서 실행 
-- 모든 public 테이블의 전체 DDL 추출
-- (컬럼, 타입, NOT NULL, 기본값, Primary Key 포함)
SELECT
  'CREATE TABLE IF NOT EXISTS ' || c.table_name || ' (' ||
  string_agg(
    c.column_name || ' ' ||
    c.data_type ||
    CASE WHEN c.character_maximum_length IS NOT NULL
      THEN '(' || c.character_maximum_length || ')'
      ELSE '' END ||
    CASE WHEN c.is_nullable = 'NO'
      THEN ' NOT NULL'
      ELSE '' END ||
    CASE WHEN c.column_default IS NOT NULL
      THEN ' DEFAULT ' || c.column_default
      ELSE '' END,
    ', '
    ORDER BY c.ordinal_position
  ) || ');' AS ddl
FROM information_schema.columns c
WHERE c.table_schema = 'public'
GROUP BY c.table_name
ORDER BY c.table_name;
💡
더 간단한 방법: 운영 프로젝트의 Table Editor에서 각 테이블의 구조(컬럼, 타입, 기본값, 제약조건)를 확인하고 개발 프로젝트의 Table Editor에서 동일하게 수동 생성해도 됩니다. 테이블이 많지 않다면 이 방법이 직관적입니다. Primary Key, Foreign Key, NOT NULL 등 제약조건을 빠뜨리지 않도록 주의하세요.

C. 테스트용 더미 데이터 삽입

SQL — 개발 프로젝트 SQL Editor 
-- 예시: 테스트 데이터 (실제 테이블에 맞게 수정)
INSERT INTO posts (title, content, user_id) VALUES
  ('테스트 게시글 1', '내용입니다', 'auth-user-uuid'),
  ('테스트 게시글 2', '두 번째 글', 'auth-user-uuid');
ℹ️
Auth를 사용하는 테이블이라면 user_id에 넣을 UUID가 필요합니다. 이 경우 Step 3 (Auth & OAuth 설정)을 먼저 완료한 뒤 개발 프로젝트에서 소셜 로그인 테스트 계정으로 회원가입을 하고, 해당 사용자의 UUID를 사용하세요. (Authentication → Users에서 확인 가능)
03

Auth & OAuth 개발 환경 설정

Supabase Auth와 Google/GitHub 소셜 로그인을 사용 중이므로, 개발 프로젝트에서도 동일하게 설정해야 합니다. 이 단계를 빠뜨리면 개발 환경에서 로그인 자체가 안 됩니다.

A. Supabase Auth 기본 설정

  1. 개발 프로젝트 대시보드 → Authentication → URL Configuration
  2. Site URL을 http://localhost:3000으로 설정
  3. Redirect URLs에 다음 두 개를 추가합니다
Redirect URLs — 개발 프로젝트에 등록 
# 로컬 개발 환경
http://localhost:3000/**

# Vercel Preview 배포 (와일드카드로 모든 Preview URL 허용)
# 아래의 username 을 본인의 Vercel 계정명으로 교체하세요
https://*-username.vercel.app/**
⚠️
운영 프로젝트의 Redirect URLs는 건드리지 마세요. 운영 프로젝트에는 운영 도메인만, 개발 프로젝트에는 localhost와 Preview URL만 등록합니다.

B. Google OAuth 개발용 설정

  1. Google Cloud Console → OAuth 2.0 클라이언트 → 새 Client ID 생성 (개발 전용)
  2. 승인된 리디렉션 URI에 개발 프로젝트의 콜백 URL을 추가합니다
  3. 개발 Supabase 프로젝트 → Authentication → Providers → Google에서 Client ID와 Secret 입력
Google OAuth — 승인된 리디렉션 URI에 추가 
# 개발 Supabase 프로젝트의 콜백 URL 형식
https://[개발프로젝트-ref].supabase.co/auth/v1/callback
ℹ️
[개발프로젝트-ref]는 개발 프로젝트의 Settings → API에서 Project URL 내의 서브도메인 부분입니다. 예: https://abcdefg.supabase.co 라면 ref는 abcdefg입니다.

C. GitHub OAuth 개발용 설정

  1. GitHub Developer Settings → OAuth Apps → New OAuth App (개발 전용으로 새로 생성)
  2. Homepage URL: http://localhost:3000
  3. Authorization callback URL: https://[개발프로젝트-ref].supabase.co/auth/v1/callback
  4. 생성된 Client ID / Secret을 개발 Supabase 프로젝트 → Authentication → Providers → GitHub에 입력
📝
운영용 OAuth 앱과 개발용 OAuth 앱을 분리하는 것이 핵심입니다. 만약 운영용 Google/GitHub OAuth 앱에 localhost를 추가해버리면, 보안상 좋지 않고 나중에 정리하기도 어렵습니다. 개발 전용 OAuth 앱을 별도로 만드세요.
04

RLS · Functions · Triggers 복제

테이블 구조만 복사하면 RLS 정책, DB Functions, Triggers가 빠지게 됩니다. 이것들도 개발 프로젝트에 동일하게 적용해야 실제 운영과 같은 환경에서 테스트할 수 있습니다.

A. RLS 정책 복제

운영 프로젝트에서 현재 적용된 RLS 정책 목록을 확인하고, 개발 프로젝트에 동일하게 적용합니다.

SQL — 운영 프로젝트에서 RLS 정책 확인 
-- 모든 RLS 정책 확인
SELECT
  schemaname, tablename, policyname, permissive,
  roles, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'public'
ORDER BY tablename, policyname;
SQL — 개발 프로젝트에 RLS 적용 예시 
-- 1. 테이블에 RLS 활성화
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;

-- 2. 운영과 동일한 정책 생성
CREATE POLICY "Users can read own posts"
  ON posts FOR SELECT
  USING (auth.uid() = user_id);

CREATE POLICY "Users can insert own posts"
  ON posts FOR INSERT
  WITH CHECK (auth.uid() = user_id);
💡
대시보드에서도 가능합니다: 각 테이블의 Table Editor → 테이블 선택 → RLS Policies 탭에서 운영 프로젝트의 정책을 확인하고, 개발 프로젝트에서 동일하게 만들어주면 됩니다.

B. DB Functions 복제

SQL — 운영 프로젝트에서 Functions 확인 
-- public 스키마의 모든 함수 정의 확인
SELECT
  routine_name,
  routine_definition
FROM information_schema.routines
WHERE routine_schema = 'public'
  AND routine_type = 'FUNCTION';

확인된 함수 정의를 개발 프로젝트의 SQL Editor에서 그대로 실행합니다. 또는 대시보드 Database → Functions에서 하나씩 확인하고 동일하게 생성할 수 있습니다.

C. DB Triggers 복제

SQL — 운영 프로젝트에서 Triggers 확인 
-- 모든 트리거 확인
SELECT
  trigger_name,
  event_manipulation,
  event_object_table,
  action_statement
FROM information_schema.triggers
WHERE trigger_schema = 'public';

확인된 트리거 정의를 개발 프로젝트에 동일하게 생성합니다.

📝
팁: 이 모든 SQL을 하나의 파일로 정리해 두세요. 프로젝트 내에 supabase/seed.sql 파일을 만들어 테이블 DDL + RLS + Functions + Triggers를 한 번에 관리하면, 나중에 개발 프로젝트를 다시 만들 때도 한 번에 적용할 수 있습니다.
05

환경 변수로 운영 / 개발 분리

같은 코드가 환경에 따라 다른 Supabase 프로젝트에 연결되도록 환경 변수를 분리합니다. 개발 프로젝트의 Settings → API에서 URL과 anon key를 확인합니다.

📁 프로젝트 루트
  ├─ .env.local ← 로컬 개발용 (개발 Supabase 연결)
  ├─ .gitignore ← .env.local 포함 필수
  ├─ supabase/
  │   └─ seed.sql ← DDL + RLS + Functions + Triggers 모음
  └─ Vercel 대시보드 → 환경별 변수 (Production / Preview)
.env.local — 로컬 개발용 
# ── Supabase 개발 프로젝트 ──
NEXT_PUBLIC_SUPABASE_URL=https://[개발프로젝트-ref].supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOi...개발키...

# 서버 사이드에서 사용하는 경우
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOi...개발서비스키...
환경 환경 변수 위치 Supabase 연결 대상 OAuth 앱
로컬 개발 .env.local 개발 프로젝트 개발용
Vercel Preview 대시보드 (Preview) 개발 프로젝트 개발용
Vercel Production 대시보드 (Production) 운영 프로젝트 운영용

Vercel 환경 변수 설정 방법

  1. Vercel 대시보드 → 프로젝트 선택 → Settings → Environment Variables
  2. NEXT_PUBLIC_SUPABASE_URL 등록 시 Production에는 운영 URL, Preview에는 개발 URL을 각각 입력
  3. NEXT_PUBLIC_SUPABASE_ANON_KEY도 동일한 방식으로 환경별 분리
  4. SUPABASE_SERVICE_ROLE_KEY를 사용 중이라면 이것도 환경별로 분리
ℹ️
Vercel은 환경 변수 등록 시 Production / Preview / Development 체크박스로 적용 범위를 선택할 수 있습니다. 같은 키 이름으로 환경별 다른 값을 넣으면 자동으로 분리됩니다.
06

로컬에서 수정 개발 & 테스트

이제 개발 Supabase에 안전하게 연결된 상태이므로 자유롭게 수정하고 테스트합니다.

Terminal 
# 개발 서버 실행
npm run dev

# 브라우저에서 확인
# http://localhost:3000

로컬 테스트 시 확인 사항

확인 항목 테스트 방법
소셜 로그인 Google/GitHub 로그인 버튼 클릭 → 정상적으로 로그인/회원가입 되는지 확인
RLS 정책 로그인한 사용자가 본인 데이터만 보이는지, 다른 사용자 데이터에 접근 불가한지 확인
DB Functions 해당 함수를 호출하는 기능을 실행하여 결과가 운영과 동일한지 확인
Triggers 트리거가 발동하는 동작(예: 데이터 삽입 시 자동 업데이트)이 정상 작동하는지 확인
새로 수정한 기능 추가/변경한 기능이 의도대로 동작하는지 확인

DB 스키마 변경이 필요한 경우

개발 프로젝트의 대시보드에서 Table Editor 또는 SQL Editor로 변경합니다. 변경한 SQL은 반드시 별도로 기록해 두세요.

SQL — 개발 프로젝트 SQL Editor 
-- 예: 새 컬럼 추가
ALTER TABLE posts
ADD COLUMN category text DEFAULT 'general';

-- 예: 새 컬럼에 대한 RLS 정책 수정이 필요하면 함께 기록
-- 예: 새 트리거가 필요하면 함께 기록
📝
변경 SQL을 프로젝트 내 supabase/migrations/ 디렉토리에 날짜별로 저장하세요. 예: 20250308_add_category_column.sql. 이 파일은 Git에 커밋하여 어떤 DB 변경이 있었는지 추적합니다.
07

커밋 → 푸시 → Vercel Preview로 최종 테스트

로컬 테스트가 끝나면 코드를 커밋하고 GitHub에 푸시합니다. Vercel은 main이 아닌 브랜치가 푸시되면 자동으로 Preview 배포를 생성합니다. 이것이 배포 전 최종 테스트 환경입니다.

Terminal 
git add .
git commit -m "feat: 검색 기능 추가"
git push origin feature/새기능이름

푸시하면 Vercel이 자동으로 Preview URL을 생성합니다. GitHub에서도 해당 브랜치에 대한 Pull Request를 생성할 수 있는 안내가 표시됩니다.

Vercel Preview URL 예시 
https://myapp-git-feature-xxx-username.vercel.app

Pull Request 생성

  1. GitHub 저장소 페이지로 이동하면 "Compare & pull request" 버튼이 나타납니다
  2. 변경 내용 설명을 작성하고 Create pull request 클릭
  3. PR 페이지 하단에서 Vercel이 자동으로 달아주는 Preview URL 링크를 확인합니다

Preview에서 반드시 테스트할 항목

항목 왜 중요한가
소셜 로그인 (Google/GitHub) Preview URL이 OAuth Redirect URI에 등록되어 있어야 작동합니다. 안 되면 3단계 Redirect URL 설정을 확인하세요.
데이터 CRUD RLS 정책 때문에 로컬과 다르게 동작할 수 있습니다.
새로 추가/변경한 기능 실제 배포 환경과 동일한 조건에서 최종 확인합니다.
💡
Preview 환경 변수를 개발 Supabase로 설정해 두었으므로, Preview URL에서의 모든 동작은 개발 DB에 영향을 미칩니다. 운영 데이터는 안전합니다.
08

PR 머지 → 운영 배포

Preview에서 문제가 없으면 Step 7에서 생성한 Pull Request를 머지합니다. Vercel은 main 브랜치에 변경이 감지되면 자동으로 Production 배포를 실행합니다.

DB 변경이 없는 경우 (코드만 수정)

  1. GitHub에서 PR 페이지로 이동
  2. 변경 내용 최종 확인 후 Merge pull request 클릭
  3. Vercel이 자동으로 Production 배포 시작
  4. 배포 완료 후 운영 사이트에서 정상 동작 확인

DB 스키마 / RLS / Functions / Triggers 변경이 있는 경우

순서가 매우 중요합니다. 코드가 먼저 배포되면 아직 없는 컬럼/함수를 참조하여 서비스 장애가 발생합니다.

배포 전 체크리스트

기본 확인 
□  feature 브랜치에서 작업했는가
□  .env.local은 개발 Supabase를 가리키는가
□  운영 Supabase에 직접 연결한 적이 없는가
□  로컬에서 주요 기능 테스트를 완료했는가
□  Vercel Preview URL에서 정상 동작을 확인했는가
□  PR을 생성하고 변경 내용을 최종 검토했는가
Auth & OAuth 확인 
□  개발 Supabase에 Auth Redirect URL이 등록되어 있는가
□  Google/GitHub OAuth 개발용 앱에 콜백 URL이 등록되어 있는가
□  Preview URL에서 소셜 로그인이 정상 동작하는가
□  로그인 후 사용자 데이터 접근(RLS)이 정상인가
DB 변경 시 추가 확인 
□  스키마 변경 SQL을 migrations/ 디렉토리에 기록했는가
□  RLS 정책 변경이 있다면 함께 기록했는가
□  Functions / Triggers 변경이 있다면 함께 기록했는가
□  운영 DB에 마이그레이션을 PR 머지 전에 적용했는가
□  운영 DB 변경 후 Table Editor에서 정상 적용을 확인했는가
