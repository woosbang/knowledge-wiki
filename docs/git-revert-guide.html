되돌리기 전 — 현재 상태 확인하기

무엇을 되돌릴지 정확히 파악하는 것이 먼저입니다. 아래 명령어로 현재 상태를 확인하고, 어떤 시나리오에 해당하는지 판단하세요.

A. 작업 디렉토리 상태 확인

Terminal 
git status

이 명령어의 출력을 보면 현재 상태를 알 수 있습니다:

출력 예시 — 수정은 했지만 커밋 전 
On branch feature/my-feature
Changes not staged for commit:
    modified:   src/app/page.tsx
    modified:   src/lib/utils.ts

Untracked files:
    src/components/NewComponent.tsx
출력 예시 — 커밋까지 완료한 상태 
On branch feature/my-feature
nothing to commit, working tree clean

B. 커밋 히스토리 확인

Terminal 
# 최근 커밋 5개 간단히 보기
git log --oneline -5
출력 예시 
a3f7b2c feat: 검색 기능 추가 (실패한 시도)
e1d9c4a fix: 버그 수정 중간 저장
b8f2d1a deploy: 최종 배포 버전    ← 여기로 돌아가고 싶음

C. 로컬과 원격의 차이 확인

Terminal 
# 원격 정보 최신화
git fetch origin

# 로컬이 원격보다 앞서 있는 커밋 수 확인
git log origin/main..HEAD --oneline
출력 해석 
# 출력이 없으면 → 로컬과 원격이 같은 상태 (푸시할 것 없음)
# 커밋이 나오면 → 로컬에만 있는 커밋 (아직 푸시 안 함)
ℹ️
위 명령어들의 결과를 종합하면 아래 3가지 시나리오 중 어디에 해당하는지 알 수 있습니다. 해당하는 시나리오로 이동하세요.
A

수정만 했고 커밋은 아직 안 한 상태

🟢 가장 간단한 경우 — 되돌리기 쉬움

파일을 수정하거나 새 파일을 추가했지만 git commit을 하지 않은 상태입니다. 이 경우 마지막 커밋 시점으로 작업 디렉토리를 깨끗하게 복원할 수 있습니다.

현재 상태:
마지막 커밋 (HEAD) ─── 수정된 파일들 (아직 커밋 안 됨)

되돌린 후:
마지막 커밋 (HEAD) ─── 깨끗한 작업 디렉토리

Step 1. 되돌리기 전 — 혹시 살릴 코드가 있는지 확인

Terminal 
# 어떤 파일이 변경되었는지 확인
git status

# 변경 내용 상세 확인 (혹시 살려야 할 코드가 있을 수 있음)
git diff

Step 2. 방법 선택 — 임시 저장 또는 완전 삭제

아래 두 가지 방법 중 하나를 선택하세요. 나중에 코드를 재활용할 가능성이 조금이라도 있다면 방법 A (stash)를 추천합니다. 완전히 버려도 된다면 방법 B (checkout)로 바로 삭제합니다.

방법 A. 임시 저장 후 되돌리기 (추천)

변경사항을 임시 보관함에 저장합니다. 저장 즉시 작업 디렉토리가 마지막 커밋 상태로 깨끗해집니다. 나중에 필요하면 꺼낼 수 있습니다.

Terminal — 임시 저장 (stash) 
# 변경사항을 임시 보관함에 저장 (저장 즉시 작업 디렉토리가 깨끗해짐)
git stash -u

# -u 옵션: 새로 만든 파일(untracked)도 함께 저장

# 나중에 다시 꺼내고 싶으면:
git stash pop

# 필요 없으면 삭제:
git stash drop

# 임시 저장 목록 확인:
git stash list
💡
git stash -u를 실행하면 변경사항이 보관함에 저장되면서 동시에 작업 디렉토리가 깨끗해집니다. 즉, stash만 하면 되돌리기가 끝납니다. 아래 방법 B를 추가로 실행할 필요가 없습니다.

방법 B. 변경사항 완전히 버리기

코드를 다시 볼 일이 없다면, 임시 저장 없이 바로 삭제합니다.

Terminal 
# 1) 수정한 파일을 마지막 커밋 상태로 되돌리기
git checkout -- .

# 2) 새로 추가한 파일(untracked) 삭제
git clean -fd

또는 checkout 대신 reset --hard를 쓸 수도 있습니다. 효과는 동일하지만 staging area까지 함께 초기화한다는 차이가 있습니다.

Terminal — reset 사용 
# 수정 파일 되돌리기 (checkout -- . 과 동일 + staging 초기화)
git reset --hard HEAD

# 새로 추가한 파일 삭제 (이건 별도로 실행 필요)
git clean -fd

각 명령어가 하는 일

명령어 역할 대상
git stash -u 변경사항을 임시 보관함에 저장하고 작업 디렉토리를 깨끗하게 복원 추적 중인 파일 + 새 파일 (복구 가능)
git checkout -- . 수정된 파일들을 마지막 커밋 상태로 복원 이미 Git이 추적 중인 파일
git clean -fd Git이 모르는 새 파일과 폴더를 삭제 새로 만든 파일 (untracked)
git reset --hard HEAD 위의 checkout과 동일한 효과 + staging area도 초기화 추적 중인 파일 + staging

Step 3. 되돌리기 완료 확인

Terminal 
git status

# 아래와 같이 나오면 성공:
On branch feature/my-feature
nothing to commit, working tree clean
B

로컬에서 커밋했지만 푸시는 안 한 상태

🟡 중간 난이도 — 로컬 커밋만 취소

git commit을 한 번 이상 했지만 git push는 아직 하지 않은 상태입니다. 커밋이 로컬에만 존재하므로, 원격 저장소(GitHub)에 영향 없이 되돌릴 수 있습니다.

현재 상태:
GitHub (origin/main) ── b8f2d1a 배포 버전
                                  ↘
로컬 (HEAD)                 ── e1d9c4a ── a3f7b2c (실패한 시도)

되돌린 후:
GitHub (origin/main) ── b8f2d1a 배포 버전
로컬 (HEAD)                 ── b8f2d1a 배포 버전 (동일)

Step 1. 되돌릴 지점 확인

Terminal 
# 원격 정보 최신화
git fetch origin

# 로컬에만 있는 커밋 확인
git log origin/main..HEAD --oneline

# 출력 예시:
a3f7b2c feat: 검색 기능 추가 (실패한 시도)
e1d9c4a fix: 버그 수정 중간 저장
# → 이 커밋들이 로컬에만 있고 아직 푸시되지 않은 것

Step 2. 방법 선택

방법 명령어 커밋 기록 파일 변경사항
완전히 버리기 git reset --hard origin/main 삭제됨 삭제됨
커밋만 취소 (코드는 유지) git reset --soft origin/main 삭제됨 유지됨 (staged)
커밋 취소 + unstage git reset origin/main 삭제됨 유지됨 (unstaged)

Step 3-① 완전히 버리기 (코드 변경사항도 모두 삭제)

로컬 커밋과 파일 변경사항을 모두 버리고, 원격(GitHub)에 푸시한 마지막 상태로 완전히 되돌립니다.

Terminal 
# 원격의 마지막 푸시 상태로 완전 복원
git reset --hard origin/main

# 새로 추가한 파일(untracked)도 삭제
git clean -fd
⚠️
--hard를 실행하면 커밋 기록과 파일 변경사항이 즉시 사라집니다. 확신이 없다면 아래의 --soft 방법을 사용하세요.
ℹ️
실수로 --hard를 실행했다면? git reflog를 실행하면 최근 HEAD 이동 기록이 나옵니다. 거기서 되돌리고 싶은 커밋 해시를 찾아 git reset --hard [해시]로 복구할 수 있습니다. 단, 커밋하지 않은 파일 변경사항은 복구할 수 없습니다.

Step 3-② 커밋만 취소하기 (코드는 보존)

커밋 기록만 제거하고, 변경한 코드는 파일에 그대로 남깁니다. 코드를 다시 살펴보고 일부만 골라서 다시 커밋할 수 있습니다.

Terminal 
# 커밋만 취소, 변경 코드는 staged 상태로 유지
git reset --soft origin/main

# 확인하면 변경사항이 staged 상태로 남아있음
git status
Changes to be committed:
    modified:   src/app/page.tsx
    modified:   src/lib/utils.ts
💡
--soft를 쓰면 코드가 남아있으므로, 필요한 부분만 골라서 다시 커밋하거나 전부 필요 없다면 그때 git reset --hard로 정리할 수 있습니다. 가장 안전한 선택입니다.

Step 4. 되돌리기 완료 확인

Terminal 
# 로컬과 원격이 같은 커밋을 가리키는지 확인
git log --oneline -3

# 원격과 비교 — 출력이 없으면 동일한 상태
git log origin/main..HEAD --oneline
C

이미 푸시까지 완료한 상태

🔴 가장 주의 필요 — 원격 저장소에 영향

실패한 코드를 이미 git push해서 GitHub에 올린 상태입니다. 이 경우 원격 저장소의 히스토리에도 영향을 줄 수 있으므로 신중하게 진행해야 합니다. 상황에 따라 두 가지 방법이 있습니다.

방법 ① git revert — 되돌리는 "새 커밋"을 만들기 (추천)

기존 커밋을 삭제하는 것이 아니라, 해당 커밋의 변경을 취소하는 새로운 커밋을 만듭니다. 히스토리가 보존되므로 팀 작업 시에도 안전합니다.

현재 상태:
b8f2d1a 배포 → e1d9c4a 실패 → a3f7b2c 실패 (HEAD, origin/main)

revert 후:
b8f2d1a → e1d9c4a → a3f7b2c → revert-1 → revert-2 (코드는 b8f2d1a와 동일)
  1. 되돌릴 커밋 해시를 확인합니다
  2. 최신 커밋부터 역순으로 하나씩 revert합니다
  3. revert 커밋을 원격에 push합니다
Terminal 
# 1) 되돌릴 커밋 확인
git log --oneline -5
a3f7b2c feat: 검색 기능 추가 (실패)     ← 이것도 되돌려야 함
e1d9c4a fix: 버그 수정 중간 저장          ← 이것도 되돌려야 함
b8f2d1a deploy: 최종 배포 버전            ← 여기로 돌아가고 싶음

# 2) 최신 커밋부터 역순으로 revert (하나씩)
git revert a3f7b2c --no-edit
git revert e1d9c4a --no-edit

# 3) 또는 범위로 한 번에 revert
git revert b8f2d1a..HEAD --no-edit

# 4) 원격에 push
git push origin main
💡
--no-edit 옵션을 쓰면 revert 커밋 메시지를 자동 생성합니다. 직접 메시지를 작성하고 싶으면 옵션을 빼면 편집기가 열립니다.

방법 ② git reset + force push — 히스토리 자체를 삭제

커밋을 히스토리에서 완전히 제거합니다. 혼자 작업하는 경우에만 사용하세요. 다른 사람이 이미 pull한 상태에서 force push하면 그 사람의 작업이 꼬입니다.

현재 상태:
b8f2d1a 배포 → e1d9c4a 실패 → a3f7b2c 실패 (HEAD, origin/main)

force push 후:
b8f2d1a 배포 (HEAD, origin/main) — 실패 커밋이 히스토리에서 사라짐
Terminal 
# 1) 돌아갈 커밋으로 로컬 리셋
git reset --hard b8f2d1a

# 2) 원격 히스토리를 강제로 덮어쓰기
git push origin main --force
⚠️
--force는 원격 저장소의 히스토리를 강제로 변경합니다. 팀원이 있거나, 해당 브랜치를 기반으로 다른 브랜치가 만들어진 경우 심각한 문제가 생길 수 있습니다. 1인 개발이고 확실한 경우에만 사용하세요.

어떤 방법을 선택해야 할까?

기준 git revert (방법 ①) git reset + force push (방법 ②)
안전성 안전 위험
히스토리 보존됨 (되돌린 기록이 남음) 삭제됨 (실패 커밋이 사라짐)
팀 작업 문제 없음 팀원 작업이 꼬일 수 있음
추천 상황 main 브랜치, 팀 프로젝트, 대부분의 경우 1인 개발의 feature 브랜치
💡
feature 브랜치에 푸시한 경우라면 force push가 오히려 더 적합합니다. feature 브랜치는 본인만 사용하는 경우가 대부분이고, revert 커밋이 쌓이면 나중에 main에 머지할 때 히스토리가 지저분해집니다. 반면 main 브랜치에 직접 푸시한 경우라면 revert를 사용하세요.
!

Vercel 자동 배포와의 관계

Vercel은 GitHub의 main 브랜치에 변경이 감지되면 자동으로 배포합니다. 따라서 main 브랜치에서 revert 또는 force push를 하면 Vercel이 자동으로 재배포됩니다.

Git 작업 Vercel 반응 결과
git revert → push 새 커밋 감지 → 자동 배포 되돌린 코드로 자동 재배포됨
git reset --hard → force push 브랜치 변경 감지 → 자동 배포 되돌린 코드로 자동 재배포됨
feature 브랜치에서 reset (main 미변경) main 변경 없음 → 배포 안 함 운영에 영향 없음
📝
DB 스키마 변경을 이미 운영 Supabase에 적용한 상태에서 코드를 되돌리는 경우, 코드는 이전 버전인데 DB는 변경된 상태가 됩니다. 이 경우 운영 DB의 스키마 변경도 함께 롤백해야 합니다. (예: 추가한 컬럼이 있다면 해당 컬럼도 제거)
+

부록: git stash 완전 가이드

git stash는 "변경사항을 임시 보관함에 넣어두는 것"입니다. 작업 중 급하게 브랜치를 바꾸거나, 되돌리기 전에 백업해두고 싶을 때 유용합니다.

명령어 설명
git stash 현재 변경사항을 임시 저장 (추적 중인 파일만)
git stash -u 새로 만든 파일(untracked)까지 함께 임시 저장
git stash push -m "설명" 설명을 붙여서 저장 (나중에 구분하기 쉬움)
git stash list 임시 저장 목록 확인
git stash pop 가장 최근 저장본을 꺼내서 적용 (보관함에서 삭제됨)
git stash apply 가장 최근 저장본을 적용 (보관함에 남아있음)
git stash drop 가장 최근 저장본을 삭제 (적용하지 않고 버림)
git stash show -p 저장된 내용의 변경사항을 상세히 확인
Terminal — 실전 사용 예시 
# 작업 중인 내용을 설명과 함께 임시 저장
git stash -u -m "검색 기능 작업 중 - 안 되면 버릴 예정"

# 이제 작업 디렉토리가 깨끗한 상태
# 다른 작업을 하거나, 코드를 리셋하거나...

# 나중에 저장 목록 확인
git stash list

빠른 참조 — 상황별 한 줄 요약

상황 명령어 위험도
수정 파일 되돌리기 (커밋 전) git checkout -- . 변경 사라짐
새 파일도 함께 삭제 (커밋 전) git checkout -- . && git clean -fd 변경 사라짐
커밋 전 한 방에 리셋 git reset --hard HEAD && git clean -fd 변경 사라짐
로컬 커밋 취소 (코드 유지) git reset --soft origin/main 코드 보존
로컬 커밋 + 코드 모두 버리기 git reset --hard origin/main 전부 사라짐
푸시 후 안전하게 되돌리기 git revert [커밋해시] → push 히스토리 보존
푸시 후 히스토리까지 삭제 (1인 개발) git reset --hard [해시] → push --force 히스토리 삭제
변경사항 임시 저장 (보험) git stash -u 안전
Git 되돌리기 가이드 — 변경사항을 마지막 커밋으로 복원하기
